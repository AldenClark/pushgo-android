## 启动可靠性入口

`scripts/run_android_startup_reliability.sh` 用受控 emulator 连续执行 App-owned `empty.clean` 功能启动，默认 50 次且零重试；详细 Oracle、双状态和 scope 边界见 `docs/quality/startup-reliability.md`。它是 Runtime/启动改动后的 opt-in 证据，不进入每次 PR，也不因 focused 50/50 自动关闭多旅程 Compose aggregate flake。

## Test-system/flake 处置

`config/quality-test-system-issues.json` 取代分类器内无 owner/到期的字符串白名单。`android-quality-precondition` 是 0 重试的准备边界；`android-compose-snapshot-observer-runtime` 是有 owner 且 2026-09-11 到期的 active flake，同样不允许自动重试。分类器只看本轮 XML，且每一个 failure 都必须精确命中 active 登记；混入一个产品断言就按产品失败。收据必须记录 issue ID，未知/过期 ID、无 ID 的 `FLAKY`、无替代证据 quarantine 都被脚本拒绝。跨平台操作规则见兄弟 Apple 仓库的 `docs/quality/test-system-issue-governance.md`。

### 设备分钟价值/成本规则

| 入口 | 设备预算 | 最高价值覆盖 | 明确不承担 |
| --- | ---: | --- | --- |
| `focused` JVM | 0 | 单一 owner 的行为/事务回归 | UI 与系统能力 |
| `focused` device | 1 个具名方法、1 次最窄旅程 | 当前修改或失败点的真实用户终点 | 邻近全类、平台排列 |
| `pr` | 0 | 全 JVM、资源/本地化、androidTest 可编译 | 设备 UI |
| `pr-ui` | 6 条最低充分正向旅程；API 37 当前 dirty byte 精确 6/6、完整增量批次 65 秒 | 准确消息、分页/已读、五域导航、Event、Channel、Gateway 的交互/数据/持久化主链 | 低频正向专项、普通错误排列、系统 UI、性能 |
| `device` | 上述 12 条 + 3 个不可下沉数据边界 | 日常正向广度 + migration/deletion/ACK 数据安全 | 全 Journey 负向集合 |
| `nightly` | 完整 Journey + data/transport/work + 消息通知/Private Service 两条系统旅程 + a11y | 跨层恢复和系统边界 | 生产分发与物理/OEM |
| `update-install` | 设备阶段 34 秒、1 次产品安装动作；默认另有两份 R8 APK 构建成本 | 下载→校验→真实包替换→重启→精确数据不丢 | 坏包/权限/OEM 笛卡尔积 |
| `release` | Nightly ∪ performance ∪ update-install ∪ release contracts | 发布前仓库内可控证据并集 | 未提供的生产账号、真机/OEM，必须 `NOT RUN` |

`pr-ui` 的“6”是代表旅程数，不是只验证 6 个节点：每条必须跨真实入口、生产状态 owner、准确数据终点与必要 relaunch。固定集只负责每次 PR 的跨 owner 早期预警；具体变更的影响选择、12 条手工 `device` 广度和 Nightly 完整类共同防止降频变成漏测。合并 refresh/标准详情、图片预览、Event/Thing 消费者、Channel 创建/改名/退订、Gateway 注册/后续请求等相同 fixture 与启动可让一次旅程保护多个用户目的；反过来，任何只增加文件、版本、tag 或节点存在断言的用例，覆盖收益按 0 计。Gateway 混合链虽含拒绝/回滚，但它保护“新网关验证并注册成功前绝不覆盖旧网关”这一已发生 P0 事务事故，保留在正向优先集合；其余普通负向分支不抢占日常预算。

固定主导航原本只对 Empty fixture 检查四个 `screen.*` tag，页面挂了错误空态或失去下一步仍能绿色。现有方法不增加启动地要求 Messages、Events、Things、Channels 的准确标题和用途说明均真实可见，Channels 还必须保留可点击的新增入口，最后才进入 Settings；focused 当前 1/1。此前同一产品 Event 指导被临时替换为错误目标时准确失败，因此本轮复用该敏感性证据，不为四个同类静态内容复制负控设备矩阵。

降频后的反向影响审计不允许只看集合包含关系：`MessageDetailScreen`、历史清理、Settings UI/ViewModel 变化均升级到完整 `device`，Update owner 因发布风险升级到完整 `release`，`ThingListScreen` 则准确聚焦 Event/Thing 两条旅程。`MessageListScreen` 的普通 loading/error/retry/布局修改只命中 messages owner，选择 `device` 下的既有分页主链；只有 Macrobenchmark、benchmark fixture、Baseline Profile 或显式性能 runner/contract 变化才进入 `performance`，与行为风险同时变化时再合并为 `release`。该成本合同防止普通页面小改丢失 focused scope 并误跑全量 Release。因而被移出固定 PR 的 Markdown、清理、筛选/刷新、Thing 三关系、解密、更新/页面显隐会在其 owner 变化时重新点亮，而不是等到 Nightly 偶然发现。若未来某个被降频目的的生产 owner 生成 `NOT_RUN`、只运行 6 条 fallback 或映射不到仓库，Lane 成本合同必须失败并恢复该目的或补齐影响规则。

- 日常顺序是 P0 正向用户目的 → 已发生事故的预警与最终结果 → 数据安全事务反例 → 普通错误恢复 → 低频平台/输入组合。前两级仍有缺口时，不主动扩展后两级。
- 新设备用例只有在保护尚未证明的用户目的、以准确功能/数据结果为最终 Oracle、且不能用低层合同或并入现有旅程同等证明时才进入 `pr-ui`。优先复用 fixture、Activity 和已有 relaunch；文件、版本、tag/节点存在及测试 Runtime 状态不计算覆盖收益。
- 数据丢失、错误成功态、未验证即覆盖旧配置、崩溃、安全问题和真实事故反例可以保留阻断性负控；其余权限拒绝、损坏输入、对称 Undo、系统/OEM 组合只在 owner 变化时 focused，或进入 Nightly/Release/`NOT RUN`。
