# PushGo Android engineering rules

- A test proves product behavior only when it reaches a user-visible, Room, network, notification, service, or OS result. `testTag`, Manifest declarations, fixture files, version strings, and Automation State are diagnostics, not sufficient oracles.
- Map behavior changes to `docs/quality/capability-coverage.md` and add the smallest test that fails when the intended user outcome breaks.
- After edits, run `scripts/quality_changed.sh` (or pass explicit `--base/--head`) to enforce the deterministic minimum lane. The generated impact plan is a lower bound, so continue through callers, ViewModels, Room, errors, Services/Workers/Receivers, and OS consumers. Never bypass an unmapped product path; map the actual capability first.
- Changes to impact rules, test architecture, or AI testing policy must keep `config/quality-ai-task-history.json` at ten or more real tasks and pass `python3 scripts/quality_ai_history.py --check`. The replay proves selector/lane/co-change contracts only; use its blind packets for an isolated semantic review and never turn recorded prose into an automatic AI score.
- Run focused tests while editing and `scripts/quality_test.sh pr` before handing off product changes. If a change affects Compose UI, navigation, Room queries/migrations, persistent mutations, loading/error/retry behavior, or a quality fixture/test seam, also run `scripts/quality_test.sh device` on one representative emulator before handoff. The scheduled nightly lane provides daily device coverage without forcing the emulator cost onto every unrelated PR. For documentation/CI-only changes, syntax/static validation is sufficient when the product lane is explicitly `NOT RUN`.
- Use `TEST_FILTER=<JVM class-or-method> scripts/quality_test.sh focused` for JVM tests and `ANDROID_TEST_CLASS=<instrumented class-or-method> scripts/quality_test.sh focused` for device tests. Do not pass an instrumented class to the JVM filter or bypass the selected emulator with an implicit connected-device fan-out.
- Keep broad input permutations in JVM/property/Room tests and a small number of representative Compose/device journeys. Do not create device × locale × state × fault Cartesian products.
- UI changes cover affected loading/content/empty/error/retry states and assert accurate displayed data or action results. Persistent behavior must be checked after repository recreation or relaunch where applicable.
- Localization-resource changes must pass `python3 scripts/verify_android_localizations.py`. Changes that can affect text wrapping, control reachability, sheets, navigation, IME, or accessibility semantics must run `scripts/quality_test.sh accessibility` when the representative Android task is in scope; resource completeness and one real large-font task are separate required claims.
- Performance-sensitive Room/data changes require correct content plus `scripts/quality_test.sh performance`; TTID/TTFD/frame/resource changes additionally require the applicable Release-like physical Macrobenchmark before that scope can pass. Proxy files, synthetic containers, sleeps, or emulator timing do not count as physical performance.
- Retries may recover classified emulator/runner faults only, never product assertion failures.
- A known test-system exception is valid only when its exact signature has an active owner in `config/quality-test-system-issues.json`; active flakes expire, allow at most one retry, and must appear by ID in the receipt. Unknown, expired, mixed product failures, or unbacked quarantine never receive flaky treatment.
- Report `PASSED`, `FAILED`, `FLAKY`, `BLOCKED`, and `NOT RUN` separately. Emulator success does not prove real FCM, permission, Doze, reboot, installer, or physical accessibility behavior.
- Treat `build/quality-results/*-summary.json` as an execution receipt, never as whole-product coverage. `selected_claims` states intent; only `executed_claims` completed. Keep product and test-system status separate.
- Update the capability matrix and Apple workstream progress record when scope/evidence changes. The cross-platform policy is `../pushgo/design/workstreams/pushgo-quality-testing-overhaul/ai-development-policy.md` when both repositories are checked out as siblings.
